## Discovered conflict

*What actually conflicted, as an observation rather than a conclusion.*

Two rows leave `repairing` for the review-repair case; one is gated, one is not:

| From | To | Trigger (as written) | Predicate |
| --- | --- | --- | --- |
| `repairing` | `verifying` | the repaired tree is ready to re-verify … Take this row for a review repair | gated — `build.md` READY, clean tree, `HEAD` on branch, no protected path |
| `repairing` | `reviewing` | the repair was driven by a review `CHANGES` verdict, so the round re-runs (CR-002) | **unconditional** — always satisfied |

The CR-002 fix added `repairing` → `reviewing` so a review repair was not a dead
end. CR-006's own record (`factory/changes/CR-006.md`) identifies that row as the
route that *skipped* the gate. Option C added `repairing` → `verifying` beside it
rather than replacing it, and ENG-116's third review pass rewrote the new row's
trigger to state what its predicate actually tests. Both rows still claim the
review-repair case, and the CR-002 row is still unconditional, so the routing
ambiguity stands.

Two consequences, both stated as source facts below:

1. **A diff-changing repair may still skip the gate.** Part B makes the stale
   package *caught* at `reviewing` → `awaiting_human_review`, not *impossible*:
   an orchestrator that takes the unconditional row for a diff-changing repair
   reproduces the CR-006 defect, and if the package is missing, unreadable, or
   names an unresolvable ref, it surfaces only at the handoff (precondition 2 /
   INV-04).
2. **The bypass also skips the protected-path gate.** `protectedPathCheck` is
   called *only* from `entryToVerification`. A diff-changing repair routed via
   `repairing` → `reviewing` reaches approval and handoff with a
   `protected_paths` hit never checked — precondition 4 covers a clean tree at
   approval, but no precondition covers protected paths. Options A and B fix
   this; Option C does not.

## Inference

Retiring the CR-002 row, or giving it a real predicate, is a behaviour change
outside CR-006 Option C. It was therefore recorded here rather than fixed
silently, per AGENTS.md's conflict protocol.

## Decision needed

**Which of these should the pack adopt?**

- **Option A — retire `repairing` → `reviewing`.** Every review repair goes
  `repairing` → `verifying` → `reviewing`: one route, always re-gated, and the
  protected-path check always runs. Costs a gate re-run for a repair that did
  not change the diff (rare). **Recommended** — smallest change, closes both
  consequences.
- **Option B — differentiate the triggers.** Keep both rows, but give
  `repairing` → `reviewing` a real predicate: the repair did not change the
  diff, i.e. `evidence` already names the branch tip (the `evidenceMatchesChange`
  helper CR-006 introduced). The trigger text becomes true and the protected-path
  question still needs an answer for the no-diff case.
- **Option C — leave as is.** Part B catches the stale case; the
  protected-path gap remains. Accepted risk, no code change.

**Also decided here, because Part B's refusal depends on it:** from `reviewing`,
the only exits are `awaiting_human_review` (refused on a stale package),
`repairing` (needs a blocking verdict), and `needs_human`. There is no
`reviewing → verifying` row, so Part B's message ("re-run the gate against the
repaired commit") names a remediation with no edge behind it. The realistic
remedy is park → rework → `repairing` → `verifying`. If Option A or B is taken,
say so; if Option C, `SKILL.md` should name the park-and-rework route.
