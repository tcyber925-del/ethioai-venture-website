# CR-005 — §14.2 precondition 3 refuses a base branch that advanced legitimately, so an approved job cannot be handed off

**Status: DECIDED — Option A approved, 2026-11-02.** Raised 2026-11-01 while resuming
job `001-post-ux-qa-regression` (Linear ENG-109) from the OpenHands adapter
(`.agents/skills/factory-openhands/`). The job reached `awaiting_human_review`
cleanly; a human then cannot approve it.

**Affects the pack, not the job.** The job's work is sound: all four round-3
verdicts are clean (`code` PASS, `security` PASS, `scope` PASS, `visual`
NOT_APPLICABLE with a stated reason), the approver returned `DECISION: APPROVE`,
and the evidence package corresponds to the branch tip. What is broken is the
precondition gate: it fails on a base branch that moved *forward*, which the
pack's own change identity says is not a staleness case.

### The pack contradicts itself — two readings of "has not moved"

Four documents state the rule, and they do not agree. Two say a forward move
is a failure; two say it is not.

**Strict — a forward move *is* a failure:**

`reference/validator.md:359-363` (the contract `validate.mjs` implements,
`validate.mjs:26`):

> - **3** — the record names a base branch and a base commit, and the base
>   branch is still where the record says it was. **A base that moved forward
>   has moved**; `approval.md` and `state-machine.md`'s sixth invariant both
>   say a moved base invalidates a pending handoff.

`reference/state-machine.md:96`, invariant 6:

> 6. A moved base branch, a merge conflict, or a stale approval invalidates the
>    pending handoff.

`reference/recovery.md:47`:

> | Base branch moves | Invalidate the approval and re-evaluate; never proceed on a stale one. |

**Lenient — a forward move is *not* stale:**

`reference/approval.md:105` qualifies the requirement:

> 3. The base branch is known and **has not moved** unexpectedly.

`reference/approval.md:66-70` names the four staleness cases the change identity
exists to catch — and a base that moved **forward** is not one of them:

> | the case | what changes |
> | --- | --- |
> | the job branch moved | `branch_commit` changes |
> | the working tree carries uncommitted changes | `clean` becomes false |
> | **the base was rewritten** | `base_intact` becomes false — the same commit now means a different diff |
> | the evidence names another change | precondition 6 fails |

`reference/isolation.md:42` — written by the CR-003 fix one layer down — states
the lenient reading as a principle:

> **A base branch that advanced is not a violation.** The check has three
> outcomes, not two. When the difference is entirely committed — every differing
> path is clean against `HEAD` — the base branch moved because work landed on it,
> which is how this factory's own pull requests merge, and the baseline is
> refreshed rather than the job refused.

The implementation
(`.opencode/skills/factory/tools/lib/preconditions.mjs:102-150`) reads "has not
moved" as *the base branch is still at the recorded commit*, and fails on any
difference:

```js
// preconditions.mjs:133-152
if (branch.sha !== commit.sha) {
  const ancestor = gitIsAncestor(worktree.path, commit.sha, branch.sha);
  if (!ancestor.ok) return { undecidable: true, detail: ancestor.reason };
  return {
    holds: false,
    detail: ancestor.ancestor
      ? `the base branch \`${baseBranch}\` moved: it is at \`${branch.sha}\`, not the recorded \`${commit.sha}\``
      : `the base branch \`${baseBranch}\` was rewritten: it no longer contains the recorded \`${commit.sha}\``,
  };
}
```

Both branches return `holds: false`. So the code follows `validator.md` and
invariant 6 — the **strict** reading — and contradicts `approval.md` and
`isolation.md`.

**This changes what a fix has to do.** Option A is not "one predicate to match
the prose"; it is a choice about *which* prose wins, and it must also correct the
documents on the losing side (`validator.md:359-363`, `state-machine.md:96`,
`recovery.md:47`) or the pack is left contradicting itself again. The
`recovery.md:47` route — "invalidate the approval and re-evaluate" — is
documented but has no implementation at all (`tools/` contains no re-evaluation
path), so today the promise is empty in both readings.

## Why approval cannot proceed

`awaiting_human_review` has exactly two edges
(`reference/state-machine.md:45-46`, implemented at
`transitions.mjs:365,374`):

- `awaiting_human_review` → `approved_to_merge` — requires **every** §14.2
  precondition to hold, so precondition 3 fails it.
- `awaiting_human_review` → `reviewing` — the stale-approval edge. It fires only
  when a **live** approval's `diff_ref` no longer matches the current diff; it
  does not address precondition 3, and returning through a re-review lands back
  at the same failing precondition.

Nothing writes `base_commit` after isolation
(`SKILL.md:315` records it; `approval.md:33` defines it as "the commit the job
branch was cut from"). So once the base moves, precondition 3 can never hold
again for that job.

The only mechanical way to clear it is to overwrite `base_commit` with the new
tip via `--set-fields`. `base_commit` is not in the writer's `FORBIDDEN` list,
so that write is *accepted* — but it falsifies the record (the branch was not
cut from the new tip, and `changedPaths` uses `base_commit` to compute the
verified diff), which is the factory editing its own record to pass its own
check. That is the thing the pack forbids elsewhere in the same breath
("the factory never edits its own", `recovery.md`).

This is the self-defeating loop CR-003 named, one layer up: **the fix for a
wedged job lands by merging a PR into `main`, and that merge is exactly what
re-wedges the job — now at the approval gate instead of the guard.**

## Same bug class as CR-002, CR-003 and CR-004

This is the fourth instance of one defect: **a guard with no exit for the state
it meets.**

| CR | State | What the prose promises | What the machine does |
| --- | --- | --- | --- |
| CR-002 | `repairing` | "the single funnel both failure sources pass through" | one exit, guarded on a *failed check*, so a review-driven repair wedged |
| CR-003 | main-checkout guard | resume after the base branch advances | refuses a legitimately advanced base |
| CR-004 | `needs_human` | "a pause", "recoverable through `/factory go`" | terminal, no edge out |
| **CR-005** | §14.2 precondition 3 | "has not moved **unexpectedly**"; identity models only a *rewrite* as stale | fails on any forward move, with no route to re-evaluate |

CR-003 fixed the guard's comparison for the **workspace** but did not touch
precondition 3, which makes the same mistake about the **base branch**. The two
checks read the same fact — "main advanced by commits, not by hand" — and
disagree: the guard now re-baselines and proceeds; precondition 3 still refuses.

## Options

All leave the product diff untouched.

- **Option A — treat a forward move as not-stale (adopt the lenient reading).**
  Precondition 3 holds when `base_intact` is true: the base branch still
  contains the recorded `base_commit`. A base that was **rewritten** (the
  recorded commit is no longer an ancestor) still fails. This makes the code
  agree with `approval.md:66-70` and `isolation.md:42` — and **requires
  correcting the strict side** (`validator.md:359-363`, `state-machine.md:96`,
  `recovery.md:47`) so the pack stops contradicting itself. Not "one predicate":
  one predicate plus three documents.
- **Option B — record the moved base and re-verify the diff.** When the base has
  moved forward, recompute the change against the new base, re-run the affected
  checks, and update `base_commit` to the new tip — a *recorded* re-baseline, not
  a hand edit. This **keeps the strict reading** (a moved base is still a
  failure) and finally implements `recovery.md:47`'s "invalidate and
  re-evaluate", at the cost of a second verification pass. It corrects the
  lenient side (`approval.md:105`, `approval.md:66-70`) instead.
- **Option C — a human-run `/factory re-baseline <job-id>`.** A command that
  re-records `base_commit` after reporting the move, leaving the decision to a
  person. Safest, but leaves the dead end in place until a human notices.

**The choice is which prose wins.** A and B are not variants of one fix; they
adopt opposite readings of "has not moved". Either way one side of the pack must
be corrected, or the contradiction survives the fix.

## Decision needed

**When `main` has advanced *forward* (the recorded `base_commit` is still an
ancestor) and the job's own diff does not overlap the commits that moved it,
should §14.2 precondition 3 hold — adopting `approval.md` and `isolation.md`
(Option A) — or should the base move still invalidate the handoff, adopting
`validator.md` and invariant 6, with the diff re-verified against the new base
(Option B)?**

Until this is answered, job 001 cannot be approved. Its work is done, its four
verdicts are clean, and its evidence is current; only precondition 3 stands
between it and `approved_to_merge`.

## Recommendation

**Option A**, with the three strict documents corrected in the same change. The
change identity already defines staleness precisely, and it says a *rewrite* is
the stale case (`base_intact` false); a forward move leaves `base_intact` true.
`isolation.md:42` — the CR-003 fix, one layer down — already adopted exactly this
reading for the workspace guard, and the base branch moving is the *same event*
seen from two checks; leaving precondition 3 strict makes the pack disagree with
itself about one fact. Option B is the right shape if the founder wants a base
move to force fresh verification rather than be tolerated — it is the more
conservative reading, and it is the one that finally implements the documented
`recovery.md:47` route; but it costs a second verification pass and, on this job,
that pass is provably redundant (the diff does not overlap the moved commits).

Whichever option is chosen, the pack is not ours to edit under this job — the
fix belongs to a pack-update issue, and job 001 should be approved once it
exists.

## Impact

blocker fixes land on `main` before its approval, which is the normal way this
factory's work lands.
