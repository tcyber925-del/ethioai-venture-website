# CR-003 — the workspace guard has no exit once the base branch moves

**Status: OPEN — awaiting a Founder Decision.** Raised 2026-10-31 while resuming
job `001-post-ux-qa-regression` (Linear ENG-109) from the OpenHands adapter
(`.agents/skills/factory-openhands/`). The job is wedged at
`stage: "repairing"` — the CR-002 fix is merged and the edge exists, but the
guard now refuses the write that would use it.

**Affects the pack, not the job.** The job's work is sound, and the CR-002 fix
landed correctly. What is broken is the guard's comparison: it treats a base
branch that legitimately advanced as a violation, with no path to re-baseline.

## Discovered conflict

*What actually conflicted, as an observation rather than a conclusion.*

`reference/isolation.md` requires that "nothing in the main checkout changes
except `factory/jobs/`", and the guard enforces it by hashing every file and
comparing against `main-checkout.txt`, the listing taken when the job started.
Anything outside `factory/jobs/` that differs is a refusal.

That is the right check for the user's *uncommitted* work, which is what the
guard's own comment says it protects ("Only a change made AFTER the job started
is a violation"). But a **committed** change to the base branch is
indistinguishable from it. Merging a pull request — the normal way this factory's
work lands — rewrites `main`'s files, and the guard cannot tell that from someone
editing the tree by hand.

This job hit it immediately. Both of its own blockers were fixed by merging pull
requests into `main`:

```
$ git log --oneline f094b79..fd7d1e1
fd7d1e1 ENG-112: give `repairing` an exit for review-triggered repairs (#40)
b944994 ENG-109: CR-002 — `repairing` is a dead end for review-triggered repairs (#39)
```

The guard then refuses every write to the job:

```
$ node .opencode/skills/factory/tools/transition.mjs \
    --job factory/jobs/001-post-ux-qa-regression --to reviewing
refused  MAIN_CHECKOUT_CHANGED: the main checkout changed outside `factory/jobs/`: ...
exit 1
```

Seventeen paths differ. **None of them is uncommitted work**: `git status
--porcelain` is empty, and every one of the seventeen is a file the two merges
committed.

The loop this creates is self-defeating: the fix for a wedged job lands through
a merge, and that merge is exactly what re-wedges it. The pack cannot resume a
job whose blocker was fixed the normal way.

`guardMainCheckout()` (`.opencode/skills/factory/tools/lib/main-checkout.mjs:144`)
has exactly two outcomes — `ok: false` (refuse) or `ok: true, recorded: false`
(unchanged). There is no third state meaning "the checkout moved, but only by
commits, and the user's work is intact." Once the baseline and the tree diverge,
**nothing re-records the baseline**: the only writes are
`guard.recorded === true`, which happens only when the baseline file is absent.

## Why implementation could not continue safely

Every write to `job.json` goes through the guard (`transition.mjs:331`), and the
handoff makes the same check before pushing (`handoff.mjs:455`). So the refusal
is total: the job cannot change stage, record fields, or hand off. There is no
legal path out, and the pack offers no documented way to refresh a baseline —
`grep -riE 're-?baseline|refresh the baseline'` over the pack returns nothing.

Deleting `main-checkout.txt` to force a re-record would work mechanically — the
guard re-records a missing baseline — but doing it unilaterally would be the
factory editing its own safety check, which is the thing the pack forbids
elsewhere in the same breath ("the factory never edits its own", recovery.md).
So it is raised rather than done.

## Source facts

- `isolation.md`: "Never modify anything in the main checkout except
  `factory/jobs/`." … "Only a change made AFTER the job started is a violation."
- `main-checkout.mjs:144` — `guardMainCheckout()`: `ok: false` on any difference
  outside `factory/jobs/`; `ok: true, recorded: true` only when the baseline file
  is absent.
- `transition.mjs:331` and `handoff.mjs:455` — both call it; both refuse on
  `ok: false`.
- `git status --porcelain` — empty. `git merge-base --is-ancestor f094b79 main`
  — exit 0, so `base_intact` holds and no approval is invalidated.

## Options

| | Option | Change |
| --- | --- | --- |
| **A** | Re-record the baseline when the only difference is committed | `guardMainCheckout` gains a third outcome: when every differing path is clean against `HEAD` (no uncommitted modification), the baseline is refreshed and the write proceeds. The guard keeps refusing anything dirty. |
| **B** | A human-run re-baseline command | A `/factory rebaseline <job-id>` that re-records `main-checkout.txt` after reporting the differences, leaving the decision to a person. |
| **C** | Scope the guard to uncommitted changes | Compare `git status` rather than a content hash — closest to the documented intent ("the user's uncommitted work"), but it loses the check against a committed change made *during* the job. |

## Decision needed

Which option should the pack adopt, and — if Option A — is a committed change
that is clean against `HEAD` the correct test for "not the user's uncommitted
work", or should it additionally require that the difference be explained by
commits the job's own `base_commit` is an ancestor of?

## Recommendation

**Option A.** The guard's stated purpose is to protect uncommitted work, and its
own comment says so; Option A makes the implementation match that intent while
still refusing a dirty tree. Option B is safest but leaves the dead end in place
until a human notices — which is how this was found. Option C is the smallest
change but gives up a real check.

### Option A is proven, not proposed

I applied Option A to a **scratch copy** of the pack (never the installed one)
and drove the wedged job out of the refusal with it. The change is one branch in
`guardMainCheckout()`, using the pack's own read-only `git` helper:

```diff
--- a/.opencode/skills/factory/tools/lib/main-checkout.mjs
+++ b/.opencode/skills/factory/tools/lib/main-checkout.mjs
   if (outside.length > 0) {
+    // A committed change to the base branch is not the user's uncommitted work.
+    // If every differing path is clean against HEAD, refresh the baseline.
+    const dirty = outside.filter((path) =>
+      git(["status", "--porcelain", "--", path], { cwd: repoRoot }).out !== "");
+    if (dirty.length === 0) {
+      return { ok: true, recorded: true, baseline: current.text, changes: outside };
+    }
     return {
       ok: false,
       kind: "changed",
-      changes: outside,
+      changes: dirty,
       reason: `the main checkout changed outside \`${ALLOWED_PREFIX}\`: ${dirty.join(", ")}`,
     };
   }
```

Both directions were exercised, because the point of the guard is the refusal:

```
# committed only -- main advanced by two merges, tree clean
$ node .opencode/skills/factory/tools/transition.mjs \
    --job factory/jobs/001-post-ux-qa-regression --to reviewing
ok  reviewing          # exit 0, stage now `reviewing`

# uncommitted -- one user file dirtied by hand
$ echo "wip" >> README.md
$ node .opencode/skills/factory/tools/transition.mjs \
    --job factory/jobs/001-post-ux-qa-regression --to reviewing
refused  MAIN_CHECKOUT_CHANGED: the main checkout changed outside `factory/jobs/`: README.md
                       # exit 1 -- and only the dirty path is named
```

The patch is preserved verbatim in `evidence/CR-003-option-a.patch`, and the
transcript in `evidence/CR-003-option-a-verification.txt`. The installed pack is
unchanged, and job 001 is still at `repairing`.

## Impact

Job 001 (ENG-109) cannot advance. It is the only job, so the factory is stopped
entirely. The blocker is not the job's work — it is the guard's comparison.

## Affected specification

`reference/isolation.md` — "The main checkout's guard". The prose is right; the
implementation is missing the distinction between committed and uncommitted
change. A fix should also state the third outcome in the prose, since the doc
currently describes only two.

## Affected Linear issue

- **ENG-109** — the wedged job. Resumes through the CR-002 edge once this is

## Founder decision

**Option A approved, 2026-10-31.** Recorded in `CR-003.decision.md` beside this
file. The guard refreshes its baseline when the base branch has moved and every
differing path is clean against `HEAD`; it keeps refusing anything uncommitted.

Implementation ships on its own issue (ENG-113), not as a rider on ENG-109.
