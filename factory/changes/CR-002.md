# CR-002 — `repairing` is a dead end when a repair is triggered by a review `CHANGES` verdict

**Status: OPEN — awaiting a Founder Decision.** Raised 2026-10-31 while running
job `001-post-ux-qa-regression` (Linear ENG-109) from the OpenHands adapter
(`.agents/skills/factory-openhands/`). The job is currently wedged at
`stage: "repairing"` with no legal transition out.

**Affects the pack, not the job.** The job's own work is sound — one reviewer
returned `PASS`, one `NOT_APPLICABLE`, and the two `CHANGES` verdicts were both
satisfied by a commit before this CR was written. What is broken is the pack's
state machine: it has no edge that lets a review-triggered repair leave
`repairing`.

## Discovered conflict

*What actually conflicted, as an observation rather than a conclusion.*

`reference/state-machine.md` says `repairing` is "the single funnel both failure
sources pass through" — a check that failed under `verifying`, and a blocking
finding under `reviewing`. Both do enter `repairing`. But the funnel has exactly
one exit:

| From | To | Trigger |
| --- | --- | --- |
| `verifying` | `repairing` | a check failed and `retries_left` remains |
| `reviewing` | `repairing` | any verdict carries a blocking finding and `retries_left` remains |
| `repairing` | `building` | the orchestrator re-dispatches the builder **with the failing check's output** |

`reference/state-machine.md:29,33,35`; the code agrees exactly —
`.opencode/skills/factory/tools/lib/transitions.mjs` implements three edges into
`repairing` (`:232`, `:314`) and **one** edge out (`:264`).

The single exit is guarded on the *failed check*:

```js
// transitions.mjs:264
"repairing>building": (context) =>
  withEvidence(context, (checks) => {
    const failed = checks.find((check) => check?.result === "failed");
    if (!failed) return unsatisfied("the evidence names no failed check to hand to the builder");
    return satisfied(`the evidence names the failed check \`${failed.check}\``);
  }),
```

A job that arrived from `reviewing` has no failed check — `evidence.json` holds
the gate results, all `passed`, because the gate did pass. `review.md` never
tells the orchestrator to add a review finding to `evidence.json` as a check,
and `evidence.schema.json` has no category for one. So the guard can never be
satisfied for a review-triggered repair, and there is no other edge:

```
$ node .opencode/skills/factory/tools/transition.mjs --job factory/jobs/001-post-ux-qa-regression --to building
refused  INV-01/TRIGGER_FALSE: the trigger does not hold: the evidence names no failed check to hand to the builder

$ node .opencode/skills/factory/tools/transition.mjs --job factory/jobs/001-post-ux-qa-regression --to needs_human
refused  INV-01/EDGE_UNKNOWN: `repairing` -> `needs_human` is not a row in `reference/state-machine.md`

$ node .opencode/skills/factory/tools/transition.mjs --job factory/jobs/001-post-ux-qa-regression --to reviewing
refused  INV-01/EDGE_UNKNOWN: `repairing` -> `reviewing` is not a row in `reference/state-machine.md`
```

`--set stage=…` cannot help: `stage` is in the writer's `FORBIDDEN` list
(`transition.mjs:121`), so the only writer of `job.json` refuses to move it by
any route but a table edge. Verbatim transcripts and the refusal log are in
`evidence/` beside this file.

## Why implementation could not continue safely

`SKILL.md` step 8 is the pack's own instruction for this state:

> **Route a repair.** A job set to `repairing` is re-dispatched: set
> `stage: "building"` and return to step 5 with the failing check's output.

The instruction assumes a failing check's output exists. Under a review
`CHANGES` it does not, so the instruction cannot be followed and the job cannot
advance. The alternatives are all closed: no other edge leaves `repairing`; the
tool that owns `stage` forbids setting it; and `rework`/`recover` both require
the job to be at `needs_human` (`SKILL.md:618`), which is itself unreachable
from `repairing`. Continuing would mean hand-editing `job.json` — the one thing
the adapter and `SKILL.md:14` both forbid — so the run stopped instead.

This is the pack's own mandatory-stop condition: the acceptance criteria cannot
be met without changing the pack, and the pack is frozen and not ours to change
under this job.

## Options

Both leave the product diff untouched.

- **Option A — give `repairing` an exit that does not require a failed check.**
  Add a `repairing` → `reviewing` row (re-review after a review-driven repair),
  or relax `repairing` → `building` to also accept a blocking finding as the
  thing handed to the builder. Either makes the funnel the two-way junction its
  own prose already claims. This is the smallest change that matches intent.
- **Option B — split the funnel.** Give review-driven repair its own stage
  (e.g. `revising`) with its own exit, so `repairing` keeps its
  failed-check guard and the two failure sources stop sharing a state that only
  fits one of them.

## Decision needed

**How should a job that entered `repairing` from a review `CHANGES` verdict
leave it, given the pack is frozen under ENG-109?**

Until this is answered, job 001 cannot complete. The job's own work is done and
its `CHANGES` findings are already addressed; only the pack's state machine
stands between it and `reviewing` → `awaiting_human_review`.

## Recommendation

Option A. The pack already documents `repairing` as "the single funnel both
failure sources pass through"; the prose and the code disagree, and Option A
reconciles them with the fewest moving parts. Option B is cleaner if the two
failure sources are meant to stay distinguishable, but it adds a stage to a
frozen machine.

Whichever option is chosen, the pack is not ours to edit under this job — the
fix belongs to a pack-update issue, and job 001 should be resumed through the
chosen edge once it exists.

### Option A is proven, not proposed

I applied Option A to a scratch copy of the pack (never the installed one) and
drove the wedged job out of `repairing` with it. The change is two edits,
because the edge table is **parsed from `state-machine.md`** while the trigger
predicates live in `transitions.mjs`:

```diff
--- a/.opencode/skills/factory/reference/state-machine.md
+++ b/.opencode/skills/factory/reference/state-machine.md
 | `repairing` | `building` | the orchestrator re-dispatches the builder with the failing check's output |
+| `repairing` | `reviewing` | the repair was driven by a review `CHANGES` verdict, so the round re-runs |

--- a/.opencode/skills/factory/tools/lib/transitions.mjs
+++ b/.opencode/skills/factory/tools/lib/transitions.mjs
+  "repairing>reviewing": () => [satisfied("the review round re-runs after the repair")],
+
   "repairing>building": (context) =>
```

Result on the wedged job record, against a clean scratch checkout:

```
$ node .opencode/skills/factory/tools/transition.mjs --job factory/jobs/001-post-ux-qa-regression --to reviewing
ok  reviewing          # exit 0, stage now `reviewing`
```

The patch is preserved verbatim in `evidence/CR-002-option-a.patch`. The
installed pack is unchanged — `git diff HEAD -- .opencode/` is empty, and job
001 is still at `repairing`.

## Impact

Job 001 (ENG-109) is stuck at `repairing` and cannot reach handoff. Its review
findings are already fixed in commit `2c76337`; no re-review has been possible
because the job cannot leave `repairing`. The cost is a stalled QA verification
job, not a wrong outcome — and the same deadlock will hit any future job whose
first repair is review-triggered rather than gate-triggered.
