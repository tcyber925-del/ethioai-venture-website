# CR-006 — a review-triggered repair changes the diff but never re-runs the gate, leaving `evidence.json` stale

**Status: OPEN — awaiting a Founder Decision.** Raised 2026-11-01 while running
job `001-post-ux-qa-regression` (Linear ENG-109) from the OpenHands adapter
(`.agents/skills/factory-openhands/`). The round-3 repair produced a new commit;
the evidence package still named the round-1 commit.

**Affects the pack, not the job.** The job's work is sound — the round-3 repair
is docs-only, and every check re-runs green against the new commit. What is
missing is a step: the walkthrough has no route from a review-triggered repair
back through verification, so the package the approval reads is stale by
construction.

## Discovered conflict

*What actually conflicted, as an observation rather than a conclusion.*

> **Correction (2026-11-02).** Part A below says a review-triggered repair should
> "return to step 6." On re-reading the transition table, step 6 *enters*
> `verifying`, and **no edge into `verifying` exists except `building>verifying`**
> (`transitions.mjs:196`; the table lists no other row). A job at `repairing`
> cannot reach `verifying` at all: `repairing>building` refuses without a *failed
> check* (`transitions.mjs:286`, "the evidence names no failed check to hand to
> the builder"), which is precisely the case a review repair is not. So Part A is
> not "change a sentence" — it needs a **`repairing>verifying` edge** (gated as
> `building>verifying` is: `build.md` READY, worktree clean, `HEAD` on the branch,
> no protected path), the same shape CR-002's fix used to add
> `repairing>reviewing`. Part B (the transition refusing a stale package) is
> unchanged and already proven below.

`reference/fast-gate.md:44-45` requires the package to track the diff:

> If a repair changes the diff, every check affected by that change re-runs. The
> final package must correspond to the diff submitted for approval.

`evidence.json` is written in exactly one place — step 6 of the walkthrough
(`SKILL.md:366-368`):

> Run the profile's `fast_gate` inside the worktree, following
> `reference/fast-gate.md`, and write `evidence.json` per
> `schemas/evidence.schema.json`.

But step 8 routes a review-triggered repair **past** step 6 (`SKILL.md:389-391`):

> - **A review `CHANGES` verdict** — set `stage: "reviewing"` and return to
>   step 9. There is no failed check to hand the builder; the round re-runs
>   against the repaired commit.

and step 9 goes straight to `awaiting_human_review` (`SKILL.md:418-439`). There
is no edge, and no prose, that returns a review-triggered repair to step 6. A
check-triggered repair does return to step 5 (building) and re-verifies; a
review-triggered one does not.

The repair commit is a real diff change — the round-3 commit `85e3ee3` changed
three files (`docs/qa/ENG-109-post-ux-regression.md`,
`interaction-probes.json`, and a new `list-semantics.json`) over the round-1
commit `6d28cfb` the evidence named. So the rule in `fast-gate.md` applies, and
nothing carries it out.

## Why it matters — and why it went unnoticed

The transition that reaches approval-ready does not read the evidence
(`transitions.mjs:296-338`): the predicate over
`reviewing>awaiting_human_review` mentions neither `evidence` nor `diff_ref`
(0 matches). So a job with a stale package passes into
`awaiting_human_review` unchallenged.

The staleness surfaces only later, at the two places that **do** read the
package against the change:

- `INV-04` (the validator): `REF_STALE` — "the evidence names a different commit
  than the current HEAD". Observed verbatim:
  `evidence.json` named `6d28cfb…`, the branch tip was `85e3ee3…`.
- §14.2 precondition 6 (`preconditions.mjs:196-225`): "the evidence names
  `<sha>`, not the current change `<sha>` — the change that was reviewed is not
  the change being approved".

Both refuse the handoff, so the failure is caught — but only after a human has
been asked to approve, and with no documented remedy. The only writer of
`job.json` runs `INV-01`, not `INV-04` (`transition.mjs:428`), so no transition
enforces the package's currency; the check lives in a tool the walkthrough never
calls between a review repair and approval.

## What the operator had to do

Re-run the profile's full gate against the repaired tip and rewrite
`evidence.json` so every check's `diff_ref` named `85e3ee3` — i.e. perform
step 6 by hand. `SKILL.md:14` says the orchestrator does exactly this ("You write
`evidence.json` only by running the profile's fast gate yourself"), so the act is
legitimate; what is missing is the **instruction** to do it at this point, and
the transition that would require it.

Note the precedent inside this one job: the round-1 repair *did* refresh the
package to `6d28cfb`. The round-3 repair did not. Nothing in the walkthrough
distinguishes the two cases, which is why one was done and the other was not —
the step is remembered, not enforced.

## Same bug class as CR-002, CR-003, CR-004 and CR-005

The fifth instance of one defect: **a guard, or a missing step, with no exit (or
entry) for the state it meets.**

| CR | Where | What the prose promises | What the machine does |
| --- | --- | --- | --- |
| CR-002 | `repairing` | "the single funnel both failure sources pass through" | one exit, guarded on a *failed check* |
| CR-003 | main-checkout guard | resume after the base branch advances | refuses a legitimately advanced base |
| CR-004 | `needs_human` | "a pause", recoverable via `/factory go` | terminal, no edge out |
| CR-005 | §14.2 precondition 3 | "has not moved **unexpectedly**" | fails on any forward move |
| **CR-006** | review repair → verify | "the final package must correspond to the diff" | no route back to step 6; no transition enforces it |

CR-002 gave `repairing` a second exit (`repairing → reviewing`). That exit made
the review-repair loop work — but it also made it possible to reach approval
**without** re-running the gate, which is this CR. The two are connected: the
edge that fixed CR-002 opened the hole CR-006 names.

## Options

All leave the product diff untouched.

- **Option A — route a review-triggered repair back through verification.**
  Add a `repairing>verifying` edge (gated as `building>verifying` is) and change
  step 8's review case to return to **step 6** — re-run the gate, rewrite
  `evidence.json` for the repaired commit — before step 9's review round, so the
  package always corresponds to the diff the reviewers and the approver read.
  Larger than it first looked: it is a new edge plus a row plus the step-8 prose,
  the same shape as the CR-002 fix. Makes `fast-gate.md` true.
- **Option B — make the approval gate require it.** Add the package's currency
  to the `reviewing>awaiting_human_review` predicate (or to §14.2 precondition 2),
  so a stale package cannot reach `awaiting_human_review`. Enforces the rule
  where it matters, but only after the fact; the operator still has to know to
  re-run the gate. Smallest change — one predicate.
- **Option C — both.** Re-route the repair (A) *and* refuse a stale package at
  the transition (B), so the step is taken and its omission is caught.

## Decision needed

**When a repair is triggered by a review `CHANGES` verdict and it changes the
diff, should the job re-run the profile's gate and rewrite `evidence.json`
against the repaired commit before the review round — and should the transition
into `awaiting_human_review` refuse a package that does not name the current
change?**

Until this is answered, every review-triggered repair leaves a stale package that
the validator and precondition 6 later refuse, and the operator must remember to
perform an undocumented step.

## Recommendation

**Option C.** Option A alone leaves the omission undetectable — which is exactly
how this job reached `awaiting_human_review` with a package naming the wrong
commit. Option B alone tells the operator after the fact, when the human is
already being asked to approve. Together they match `fast-gate.md`'s rule with
both a step and a check, in the shape the pack uses elsewhere (a prose step, plus
a transition that refuses when it was skipped).

Whichever option is chosen, the pack is not ours to edit under this job — the fix
belongs to a pack-update issue.

### Option C is proven, not proposed

Option C has two parts. Part **A** is prose — step 8's review case returns to
step 6 before step 9 — and a prose change is proven by reading it, not by
running it. Part **B** is code, and I applied it to a **scratch copy** of the
pack (never the installed one) and drove the approval with it:

```diff
--- a/.opencode/skills/factory/tools/lib/transitions.mjs
+++ b/.opencode/skills/factory/tools/lib/transitions.mjs
@@
 import { implementedPreconditions, runPreconditions } from "./preconditions.mjs";
+import { evidenceRefs } from "./refs.mjs";
 import { reason } from "./reasons.mjs";
@@
   "reviewing>awaiting_human_review": (context) => {
     if (context.round === null) {
       return unsatisfied("the record carries no round, so the verdict files cannot be found");
     }
+    // CR-006: a review-triggered repair changes the diff without re-running
+    // the gate, so the package can name a commit other than the one being
+    // approved. `fast-gate.md`: "the final package must correspond to the diff
+    // submitted for approval." Refuse a package that names another change.
+    const worktree = worktreeOf(context);
+    const refs = evidenceRefs(context, worktree);
+    if (!refs.missing && !refs.unreadable && refs.problems.length === 0 &&
+        refs.targets.length > 0) {
+      const current = changeIdentity(context);
+      if (current.ok) {
+        const stale = refs.targets.find((target) => target.sha !== current.identity.branch_commit);
+        if (stale) {
+          return unsatisfied(
+            `the evidence names \`${stale.sha}\`, not the change being reviewed \`${current.identity.branch_commit}\` -- re-run the gate against the repaired commit`);
+        }
+      }
+    }
     for (const role of ROLES) {
```

The patch reuses the pack's own `evidenceRefs` (the ONE place a `diff_ref` is
parsed) and `changeIdentity`, so it agrees with `INV-04` and precondition 6 by
construction rather than by a second implementation.

Three cases, against the real job (never written by the proof), with the patch
applied only to the scratch pack (`evidence/CR-006-option-c-proof.txt`):

```
CASE 0 (control, unpatched): stage=reviewing, evidence diff_ref=6d28cfb, tip=85e3ee3
        -> ok awaiting_human_review   (the bug: a stale package reaches approval-ready)
CASE A (patched, stale):     refuse -- "the evidence names `6d28cfb...`, not the
        change being reviewed `85e3ee3...` -- re-run the gate against the repaired commit"
CASE B (patched, current):   ok awaiting_human_review   (no false positive)
```

The control case is the important one: it reproduces the exact hole, unpatched,
against the real job's own stale package. The installed pack is unchanged —
`git diff HEAD -- .opencode/` is empty — and job 001 is still at
`awaiting_human_review`.

## Impact

Job 001 (ENG-109) reached `awaiting_human_review` with `evidence.json` naming the
round-1 commit while the branch tip was the round-3 commit. The validator flagged
it (`INV-04/REF_STALE`) and precondition 6 would refuse the approval; the operator
re-ran the gate by hand to correct it. The cost here was a manual repair; the
recurring cost is that any review-triggered repair leaves the same latent
staleness, caught only when a human is already mid-approval.
