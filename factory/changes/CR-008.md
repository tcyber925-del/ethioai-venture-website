## Discovered conflict

*What actually conflicted, as an observation rather than a conclusion.*

ENG-119 asks for a change to the public Work index that the approved content
policy forbids.

The ticket's objective:

> Remove the **EthioBio card from the public Work index** at `/work/` because the
> founder has identified this Work entry as duplicate/redundant.

The approved MIS v1.0 "Evidence and content policy", recorded verbatim in
`src/content/projects/ethiobio.md`:

> `# Traceability (ENG-76): EthioBio is the only project named in the approved`
> `# specifications. MIS v1.0 "Evidence and content policy": "EthioBio must be`
> `# represented truthfully as In Development unless the source specification is`
> `# explicitly updated."`

and restated as a binding rule in `src/content.config.ts`:

> `Seeded value "In Development" for EthioBio is mandated by MIS v1.0.`

"Represented truthfully as In Development" is satisfied by listing EthioBio on
`/work/` with status `In Development` — which is exactly what the deployed page
does. Removing the listing removes the representation, so the requested change
requires **updating the source specification** first. ENG-119's own protocol
agrees:

> If implementation reveals that removing the listing breaks an approved product
> requirement or requires a material architectural/product decision, stop, raise a
> change request, and wait for founder approval.

## Premise not reproduced

The ticket's stated evidence is that the founder annotated the card "for removal
as a duplicate". No duplicate is reproducible in the repository or on the
deployed page.

- **Data.** The `projects` collection holds exactly two entries —
  `src/content/projects/ethiobio.md` and `src/content/projects/ethiosci.md`.
  `src/pages/work/index.astro` renders one `ProjectCard` per collection entry, and
  no entry is duplicated. There is no second EthioBio source.
- **Deployed page.** `https://ethioai-venture-website.tcyber925.workers.dev/work/`
  shows **two** project cards — `EthioBio` and `EthioSci`. There is no duplicate
  EthioBio card.
- **Tracker.** No Linear issue, repository record, or PR names this duplicate, or
  a decision to unlist EthioBio.

So the ticket requests a public-content change whose premise is not evidenced and
whose effect contradicts the approved content policy.

## Why implementation could not continue safely

An automation worker cannot resolve a conflict between a ticket and the approved
specification, and cannot unilaterally unlist a mandated project from the public
Work index. AGENTS.md's conflict protocol is explicit:

> STOP → Change Request → Founder Decision → Update Specification → Update Linear
> → Continue.

and the autonomy policy classifies this as `approval`:

> Architecture, infrastructure, security, authentication, paid services, **major
> public claims**, or V1 scope changes. Prepare context/plan and wait for explicit
> approval.

Removing a mandated project from the public Work index is a public-content /
V1-scope change. Implementing it before the decision would either violate the
approved content policy or require the worker to invent a policy update — the
failure mode CR-001 names "laundering an unrecorded founder decision into an
approved PR".

## Options

- **Option A — remove the EthioBio card from `/work/` and update the source
  specification.** Take ENG-119 as written: the Work index lists only projects the
  founder wants surfaced; the canonical detail route (`/work/ethiobio`) and the
  project content are preserved. Requires a founder decision superseding the MIS
  v1.0 policy line, plus a specification update so `src/content/projects/ethiobio.md`
  and `src/content.config.ts` no longer claim the listing is mandated. Add a
  regression test and re-run `npm run verify`.
- **Option B — add a Work-index listing flag instead of deleting.** Keep
  EthioBio's content and detail route; add an explicit, evidence-traceable
  `listed: false` (or equivalent) field so the exclusion is a recorded content
  decision rather than a deleted entry, and the `/work/` count and status chips
  stay derived. Same founder decision required; more faithful to the content
  model, which already prefers explicit optional fields over deletion.
- **Option C — decline as not-reproducible.** No duplicate exists, so there is
  nothing to remove; close ENG-119 as won't-do with the evidence above. No code
  change. This is the option the current evidence supports, but it overrides a
  stated founder annotation, so it is a founder call, not a worker call.

## Linear update

Recorded on ENG-119: conflict raised, decision requested, automation halted
before any code change.
After CR-007 Option A, `repairing` has exactly two rows out, and both can
refuse for the same job:

| From | To | Predicate | When it refuses |
| --- | --- | --- | --- |
| `repairing` | `building` | `evidence.json` names a **failed** check | a review repair's package is all-passed — there is no failed check to hand over |
| `repairing` | `verifying` | `entryToVerification` — `build.md` READY, clean tree, `HEAD` on the branch, **no protected path** | the repair touched a protected path, or `build.md` is not READY, or the tree is dirty |

There is no `repairing` → `needs_human` row. So a review repair whose diff
touches a protected path reaches a state where **every** exit refuses: it fails
safe — it can never reach approval — but it cannot be parked, and `SKILL.md`
steps 5 and 6 tell the orchestrator to "set `stage: \"needs_human\"` … and stop".

Two refinements the PR review raised, recorded here for the decision:

- "waits for a human" understates it. The job is not parked; it sits at
  `repairing` indefinitely, with no `job.json` field marking that it is stuck.
- A job wedged here also cannot take the `needs_human` → `repairing` rework
  path (`reference/recovery.md`), because it never reaches `needs_human`. So
  the only recovery is out-of-band: a human edits the profile/path list or the
  worktree, then resumes. Whichever option is chosen should say how a human
  clears a wedged job.

This is the mirror of the defect CR-007 fixed. Before CR-007, the unconditional
`repairing` → `reviewing` row was the escape; retiring it closed a silent bypass
and opened an explicit dead end. The trade is the right one — a job that stops
and waits for a human beats one that approves unchecked — but the dead end is
real and unnamed in the pack's prose.

## Decision needed

**Which of these should the pack adopt?**

- **Option A — add a `repairing` → `needs_human` row.** A repair that cannot
  reach either `building` or `verifying` parks with its cause. Matches `SKILL.md`
  steps 5 and 6, which already assume the edge exists. A transition into a failure
  stage is always permitted by the validator's own rule ("failing safe must
  never be blocked"), so the predicate is trivial. **Recommended** — smallest
  change, and it makes the prose true.
- **Option B — add a `repairing` → `blocked` row.** Same shape; `blocked`
  carries a required `cause` in the schema. Semantically "cannot proceed
  without a human", which is what happened.
- **Option C — document the park-and-rework route without a new edge.** Say in
  `SKILL.md` that a repair which cannot re-enter verification is reworked by a
  human through `/factory rework`. No code change; the job still cannot be
  parked by the orchestrator, so steps 5 and 6's instruction stays false.

Whichever is chosen, the decision should also say whether the protected-path
case specifically should offer a human-decides route rather than a bare park —
the path is protected precisely because a human must decide.
