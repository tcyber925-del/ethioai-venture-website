# CR-004 — `needs_human` is a terminal state with no resume edge, so a granted rework cannot be spent

**Status: OPEN — awaiting a Founder Decision.** Raised 2026-11-01 while running
job `001-post-ux-qa-regression` (Linear ENG-109) from the OpenHands adapter
(`.agents/skills/factory-openhands/`). The founder granted `/factory rework`, the
budget was restored, and the job still cannot move.

**Affects the pack, not the job.** The job's own work is sound; its two round-2
blocking findings are documentation-accuracy defects with precise, quoted
remediation. What is broken is the pack's state machine: it documents
`needs_human` as a resumable pause, and implements it as a terminal state with no
edge out.

## Discovered conflict

*What actually conflicted, as an observation rather than a conclusion.*

Three documents describe `needs_human` as recoverable, and the machine
implements it as terminal. Both readings are quoted verbatim below.

`reference/state-machine.md:13` lists it as terminal:

> Terminal: `merged`, `blocked`, `needs_human`, `rejected`, `cancelled`.

`reference/learning.md:15-18` says the opposite in the same breath:

> **a job parked at `blocked` or `needs_human`, when a human asks for its record.**
> Both are terminal transitions but neither is an outcome: `blocked` is
> recoverable through `/factory go`, and `needs_human` is a pause.

`reference/recovery.md:32-34` makes resuming the designed path:

> Resuming is a separate, human-gated act. `recover` reports what would come next;
> a human then runs `/factory go <job-id>`, which carries the resume guarantees.

And `SKILL.md:626-631` (`/factory rework`) ends by naming the resume door:

> **Report and stop.** State the job, the restored budget, the timestamp, and
> the stage that would run next. Re-running the job itself is the human's act
> via `/factory go`.

The transition table has no row whose `From` is `needs_human`, and the code
agrees — `.opencode/skills/factory/tools/lib/transitions.mjs` implements 20 edges
and none of them leaves `needs_human` or `blocked`. `/factory go` is the named
resume door, but its own precondition (`SKILL.md:455`) is *"Job at
`awaiting_plan_approval`"* and its failure behaviour is *"If stage mismatches,
report and stop"* — so it cannot resume a job at `needs_human` either.

Every exit is refused. The refusals, verbatim, are in
`evidence/CR-004-refusals.txt`; the load-bearing ones:

```
$ node .opencode/skills/factory/tools/transition.mjs --job factory/jobs/001-post-ux-qa-regression --to repairing
refused  INV-01/EDGE_UNKNOWN: `needs_human` -> `repairing` is not a row in `reference/state-machine.md`

$ node .opencode/skills/factory/tools/transition.mjs --job factory/jobs/001-post-ux-qa-regression --to reviewing
refused  INV-01/EDGE_UNKNOWN: `needs_human` -> `reviewing` is not a row in `reference/state-machine.md`

$ node .opencode/skills/factory/tools/transition.mjs --job factory/jobs/001-post-ux-qa-regression --to awaiting_human_review
refused  INV-01/EDGE_UNKNOWN: `needs_human` -> `awaiting_human_review` is not a row in `reference/state-machine.md`

$ node .opencode/skills/factory/tools/transition.mjs --job factory/jobs/001-post-ux-qa-regression --set-fields --set stage=reviewing
refused  FIELD_NOT_WRITABLE: a field write may not set `stage` -- `handoff` belongs to the guarded tool alone, and the rest identify the job
```

`--set stage=…` cannot help: `stage` is in the writer's `FORBIDDEN` list
(`transition.mjs:121`), so the only writer of `job.json` refuses to move it by
any route but a table edge.

## Why the rework could not be spent

`/factory rework` did exactly what it promises, and that is the problem. Step 3
(`SKILL.md:626-628`) says:

> **Reset only two fields.** In one write, set `retries_left` to the profile's
> budget and `retry_budget_reset_at` to the current UTC timestamp … Touch no
> other field — especially not `stage`, `diff_ref`, or `round`.

The rework was executed and accepted:

```
$ node .opencode/skills/factory/tools/transition.mjs --job factory/jobs/001-post-ux-qa-regression \
    --set-fields --set retries_left=2 --set retry_budget_reset_at=2026-11-01T14:53:42Z
ok  needs_human
```

The record now reads `stage: needs_human`, `round: 2`, `retries_left: 2`,
`retry_budget_reset_at: 2026-11-01T14:53:42Z`. The budget is restored and there
is no legal way to spend it: `repairing` is where a repair spends a retry, and no
edge reaches `repairing` from `needs_human`. The job has a fresh budget and no
door.

This is the pack's own mandatory-stop condition: the acceptance criteria cannot be
met without changing the pack, and the pack is frozen and not ours to change under
this job. Continuing would mean hand-editing `job.json`, the one thing the adapter
and `SKILL.md:14` both forbid.

## Same bug class as CR-002 and CR-003

This is the third instance of one defect: **a guard with no exit for the state it
meets.**

| CR | State | What the prose promises | What the machine does |
| --- | --- | --- | --- |
| CR-002 | `repairing` | "the single funnel both failure sources pass through" | one exit, guarded on a *failed check*, so a review-driven repair wedged |
| CR-003 | main-checkout guard | resume after the base branch advances | refuses a legitimately advanced base, so the CR-002 fix re-wedged |
| **CR-004** | `needs_human` | "a pause", "recoverable through `/factory go`" | terminal, no edge out; the named resume door excludes it |

CR-002 and CR-003 were both found only by running a job, never by reading the
pack — and neither fix addressed the class. CR-004 is the same shape, so the fix
should be checked against the class, not just this instance: after it, ask which
other states the prose calls resumable and the machine leaves terminal.

## Options

Both leave the product diff untouched.

- **Option A — give `needs_human` a resume edge that spends the re-granted
  budget.** Add a `needs_human` → `repairing` row whose trigger requires a human
  rework to be recorded (`retry_budget_reset_at` set) and the budget to hold a
  retry. This makes `/factory go`'s documented role real for a parked job, and
  keeps the loop from spinning: the resume *spends* a retry, so a job with a
  spent budget still cannot move. Smallest change; matches the prose.
- **Option B — separate "park" from "resume" explicitly.** Give the parked states
  a documented resume row per destination (`needs_human` → `repairing` for a
  rework, `blocked` → `building`/`planning` for a recovered cause), so the
  recovery document's "recoverable" claim is backed by an edge per failure kind.
  More faithful to `recovery.md`'s per-failure routing, at the cost of more rows.
- **Option C — make the terminal line true.** Declare `needs_human` truly
  terminal, delete the "recoverable through `/factory go`" prose from
  `learning.md` and `recovery.md`, and make `/factory rework` refuse rather than
  hand back a budget that cannot be spent. Honest, but it removes the recovery
  path the pack is built around; not recommended.

## Decision needed

**How should a job at `needs_human` that has been granted a rework leave that
state, given the pack is frozen under ENG-109?**

Until this is answered, job 001 cannot complete. Its work is done and its round-2
findings have precise remediation; only the pack's state machine stands between
the re-granted budget and its use.

## Recommendation

Option A. The pack already documents `needs_human` as "a pause" and names
`/factory go` as the resume door; Option A makes the code agree with that prose
with one row and one predicate, and preserves the anti-spin property because the
resume spends a retry. Option B is the right shape if `recovery.md`'s per-failure
routing is meant to be mechanical rather than descriptive. Option C is only
correct if the pack intends to abandon recovery entirely.

Whichever option is chosen, the pack is not ours to edit under this job — the fix
belongs to a pack-update issue, and job 001 should be resumed through the chosen
edge once it exists.

### Option A is proven, not proposed

I applied Option A to a scratch copy of the pack (never the installed one) and
drove the reworked job out of `needs_human` with it. Two edits, because the edge

Three cases, against a clean scratch checkout (`evidence/CR-004-option-a-proof.txt`):

```
CASE A (rework recorded, budget 2):
ok  repairing          # stage -> repairing, retries_left 2 -> 1, round 2 -> 3

CASE B (no rework stamp, budget 2):
refused  INV-01/TRIGGER_FALSE: the trigger does not hold: no human rework is recorded, so the job may not resume
```

The refusal case matters as much as the permit: the resume spends a retry, so the
anti-spin rule (invariant 5) still holds. The installed pack is unchanged —
`git diff HEAD -- .opencode/` is empty, and job 001 is still at `needs_human`.

## Impact

Job 001 (ENG-109) is parked at `needs_human` with a restored budget it cannot
spend. Its review findings have precise remediation; no re-review has been
possible because the job cannot leave `needs_human`. The cost is a stalled QA
verification job, not a wrong outcome — and the same dead end will hit any future
job a human reworks after a review deadlock, which is exactly the case
`/factory rework` was written for.
