# Founder Decision — CR-007

Date: 2026-11-02

I approve **Option A** — retire the `repairing` → `reviewing` row. Every review
repair goes `repairing` → `verifying` → `reviewing`: one route, always
re-gated, and the protected-path check always runs.

The row was added by the approved CR-002 fix (ENG-112) so a review repair was
not a dead end. CR-006 Option C (ENG-116) then added a gated
`repairing` → `verifying` edge beside it rather than replacing it, so both rows
still claim the review-repair case and the ungated one still exists. Retiring
it is the smallest change that closes both consequences the CR names: a
diff-changing repair can no longer reach approval without the gate, and the
protected-path check — reached only from `entryToVerification` — can no longer
be skipped by routing a repair through `reviewing`.

This is not a one-predicate fix. Three further places state the direct row, and
they must be corrected in the same change or the pack stays self-contradictory:

- `reference/state-machine.md:41` — the row itself (the table goes 25 → 24 rows)
- `reference/state-machine.md:124` — "The direct `repairing` → `reviewing` row
  (CR-002) remains: the round may re-run without re-gating"
- `SKILL.md:405-406` — "The direct `repairing` → `reviewing` row still exists
  for a repair that does not change the diff"
- `reference/validator.md:92` — "The table has 25 rows"

The cost is a gate re-run for a repair that did not change the diff. That case
is rare, and a re-run is idempotent, so the trade is one extra gate run against
a silent bypass of both the gate and the protected-path check.
